# Phase 0 — Design Partner Validation

**Project:** Ledger Integrity & Audit Intelligence Platform
**Source:** BRD v1.0 (15 Aug 2026), Section 21 — Phase 0
**Goal:** Validate the real audit/GST workflow with five CA/GST design partners *before* building the product broadly.

## Phase 0 deliverables (per BRD §21)

| Deliverable | Location | Status |
|---|---|---|
| Design-partner kit (brief, questionnaire, data request, pilot outline) | `design-partner-kit/` | Draft v0.1 |
| Anonymised / synthetic sample datasets | `sample-data/` | Generated (synthetic, seeded anomalies) |
| Rule prioritisation matrix (MVP rule pack, BRD §21.1) | `rule-prioritisation/` | Draft v0.1 |
| Sample workpaper (journal-entry testing) | `sample-workpaper/` | Template + filled example |
| Security requirements baseline | `security/` | Draft v0.1 (from BRD §19) |
| Workflow spike — rules running end-to-end on sample data | `spike/` | Working |

## What "done" means for Phase 0 (exit criteria)

1. Five design partners recruited; discovery interviews completed and written up.
2. Partners have ranked the MVP rule pack (rule-prioritisation matrix signed off).
3. At least one real (anonymised) partner dataset imported and reconciled to its trial balance.
4. The sample workpaper reviewed by a CA partner and judged "review-ready" in structure.
5. Security requirements baseline accepted by partners' IT/security contacts.
6. Go / no-go decision for Phase 1 (MVP) recorded.

## Important notes

- All data in `sample-data/` is **synthetic** — generated by `sample-data/generate_data.js` with a fixed seed. No real client data is present anywhere in this repository.
- Seeded anomalies (the "ground truth" the product must find) are documented in `sample-data/SEEDED_ANOMALIES.md`.
- The spike in `spike/` is a throwaway proof of workflow, **not** MVP code.
